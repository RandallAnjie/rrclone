# Cloudreve

[Cloudreve](https://cloudreve.org) is a self-hosted file management
and sharing system. This backend talks to the **Cloudreve v4** API
(`/api/v4`) of the community and Pro editions. Cloudreve v3 servers
are not supported.

## Configuration

You need the URL of the site, and one of:

- **Email and password.** Two-factor authentication is supported:
  `rclone config` asks for the code.
- **An OAuth app.** This also works for accounts which sign in with
  OIDC / single sign-on (Pro), or sites with a login captcha. An
  administrator creates the app under Dashboard → OAuth Apps:
  - Redirect URI: `http://127.0.0.1:53682/`
  - Scopes: `openid`, `offline_access`, `UserInfo.Read`,
    `Files.Read`, `Files.Write`, `Shares.Write`

  Then enter its client ID and secret in `rclone config`. Leave
  `email` blank.

Here is an example of how to make a remote called `remote`. First run:

```console
rclone config
```

```text
n) New remote
name> remote
Storage> cloudreve
client_id>
client_secret>
url> https://cloud.example.com
email> me@example.com
password> *** (y to type it)
Edit advanced config?
y/n> n
Two-factor authentication code
config_2fa> 123456
```

Then list your files with:

```console
rclone lsd remote:
```

rclone keeps the access and refresh tokens in the config and refreshes
them. With email and password configured, rclone logs in again when the
refresh token expires, unless the account uses 2FA. Then run
`rclone config reconnect remote:`.

### Share links

Set `share_id` (the `AbCd` of `https://cloud.example.com/s/AbCd`) and,
if needed, `share_password` to browse a share link. The remote is read
only, and needs no login unless the share requires one.

### Storage policies (Pro)

In Cloudreve Pro a user group can have several storage policies. Set
`policy_id` to upload to a particular one. Otherwise uploads use the
policy of the target folder.

## Uploads

rclone uploads the way the storage policy says:

| Policy | How rclone uploads |
| --- | --- |
| Local, or any policy with relay on | In chunks through the Cloudreve server |
| Slave node (remote) | In chunks straight to the node |
| OneDrive | Straight to the OneDrive upload session, then tells Cloudreve |
| S3, KS3, COS | Presigned multipart upload, then tells Cloudreve |
| OSS, OBS | Presigned multipart upload; the provider tells Cloudreve |
| Qiniu | Qiniu multipart upload v2; Qiniu tells Cloudreve |
| Upyun and others | Through the Cloudreve server in one request, which the server limits in size; enable relay for big files |

Chunks are buffered in memory, so a failed chunk is retried. A relayed
upload with no chunk size is sent in one request.

Uploading over an existing file stores the new data as a new version.
Cloudreve keeps or prunes old versions by its own settings.

### Encryption

If the storage policy encrypts files and uploads don't go through the
server, Cloudreve expects the client to encrypt with AES-256-CTR.
rclone does this, so files are stored encrypted and Cloudreve decrypts
them on download. Set `client_encryption = false` to upload unencrypted
instead. Relayed uploads are encrypted by the server.

## Limitations

- Cloudreve exposes no file hashes, so checks use size and modification
  time.
- The modification time is set at upload, with one second precision.
  It can't be changed afterwards, so changing it means re-uploading.
- Empty files uploaded straight to object storage (no relay) get the
  current time, as Cloudreve has nothing to upload them to.
- Server-side copy only works between different folders. Within one
  folder rclone downloads and uploads.
- Files go to the trash when deleted, unless `hard_delete` is set.
- Names can't contain `\ / : * ? " < > |`. rclone encodes these
  characters, see [encoding](/overview/#encoding).
- Removing a public link with `rclone link --unlink` isn't supported.
  Delete it on the web.
